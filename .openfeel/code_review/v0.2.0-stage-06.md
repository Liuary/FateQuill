## 二、核心结论与经验

1. **四维执行机制必须逐维定稿（REV-001 high）**：v1 计划定义了 Evaluator 接口却未裁决各维「LLM-as-judge / 规则 / 混合」路径，也未声明与 stage-03 引擎契约的对接方式。定稿：剧情/世界观/真人感 = LLM-as-judge（经 `ModelProvider` **非流式收口**）、合规 = 规则引擎（无需 Token），落点 `src/orchestration/review/`，JSON 容错降级不抛穿，LLM 维夹具回放。
2. **持久化迁移与关联键缺口须先补（REV-002 high）**：schema 无 review 表 → 迁移 v3 `review_record`（插件纪律 + 幂等复验）；关联语义简化为 `chapter_id + round`（生成会话 `requestId` 内存态不持久化，显式声明）。
3. **版本模型是 T3/T4/T5 的共同前置（REV-003）**：定稿「版本池 = 初版 + 重写轮次产物（会话级）」+ 择优 = 加权总分 + 采纳经 `EditorController.replaceContent(html)`（单条撤销，需扩展 stage-04 命令面）。
4. **rubric 与合规规则载体须显式（REV-004）**：`docs/review-rubric.md`（版本化 + 内联 prompt + 四维子维度）+ `compliance-rules.ts`（版本化 + 覆盖有限声明）+ 合规低分**仅人工裁决不自动重写**。
5. **重写回路细则须数值化（REV-005）**：上限 2、反馈注入（上轮 score+reasons）、产物入池不自动替换、默认开可关。
6. **成本放大须声明（REV-006）**：四维审查 + 重写使每章 LLM 调用约为纯生成 4~5 倍；复用默认模型、非流式收口、沿用预算裁剪、Token 提示。
7. **可判定性补强（REV-007）**：样本集入库、可回溯查询口径、M2 素材库边界声明（归 stage-07）、stage-05 REV-009 并入首 op。
8. **合规自动动作须隔离（REV-008 代码级落实）**：`triggerDims = failedDims \ {compliance}` 三处隔离（loop/rewrite/UI），避免自动重写放大合规误判。
9. **采纳临时 controller 须 dispose（REV-008）**：`adopt` 每次新建 `EditorController` 会累积 composition DOM 监听器 → `try/finally dispose`（已代码修复，REV 待收口）。
