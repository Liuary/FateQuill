## 二、核心结论与经验

1. **落地交互模式分叉须用户拍板（REV-001 high）**：v1 计划描绘「生成态 store + 预览面板 → 显式插入」，与 stage-04 已交付的 `EditorController` 流式直插机制互斥，且与大计划 M1「流式插入」措辞冲突。审查官识别为**交互/投资决策**（性能约束两模式等价，不构成裁决依据），提交用户拍板 → **ADR-002 模式 A 流式直插**（accepted）。教训：跨阶段接口定稿前须核对既有交付物，避免投资空转（C-08）。
2. **store 边界与可判定性口径（REV-002）**：要求列 `generationStore` 元状态清单（不持正文）、指定 C-03 测量工具（React Profiler `onRender`）、精确「快照不变」口径（豁免 `saveStatus/lastSavedAt` 自动保存域）、声明双 store 隔离机制。
3. **分层 E2E 定稿（REV-003）**：拒绝为 v0.1 从零建 tauri-driver（成本/收益低）；定三层验收（Rust 往返 / Vitest mock 全链路 / 真机冒烟检查单），「重启不丢」以一条手测承载。
4. **装配细则数值化 + 模板版本化（REV-004）**：预算（系统 1k / 设定卡 2k / 前文 2k / 总 8k）、裁剪序（设定卡→前文）、落点与版本常量、provider 无关（输出 `ChatOptions`）全部定稿。
5. **阶段中间态需自洽（REV-008）**：op-003 的 `stop()` 在 aborted 分支不复位 store → 残留「半态」；op-003 即补 `reset()` 收敛，而非留给 op-004 补救。
6. **人工协验待办显式声明（REV-009）**：真实 WebView 操作无法自动化，执行者显式声明待办（非隐瞒）；列入 v0.1 收口协验清单，M1 前须闭合。
7. **E2E 声明与交付一致性（generation BUG-001）**：op-006 声明「真链路下 C-03 成立」，但 E2E 只覆盖代理指标。测试官以最小复现指出不一致 → 修复为 `vi.mock("@tiptap/react")` 把真实 `EditorContent` 包进 `<Profiler>` + 非空洞性守卫，独立探针验证插桩生效。
8. **登记数值失真（build BUG-001）**：chunk 体积登记「311KB / gzip 97KB」与实测（~850KB / ~268KB）严重不符（gzip 比一致，疑似早期误记沿用）。活文档更正为实测值，历史评审记录保留留痕不改。
