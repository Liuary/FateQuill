## 1. 项目目标

### 1.1 定位
**FateQuill（中文名：命笔）** 是一款**开源桌面应用**，以多 Agent 编排辅助创作者完成长篇小说创作，并把「去 AI 味」作为可研究、可积累的学术内核。

### 1.2 双核心目的（一等公民，贯穿全部版本）
1. **实现创作者的构想**：把创作者意图转化为可控、可审阅、可迭代的小说文本。
2. **研究「去 AI 味」**：让 AI 写出简练、有人味的文字——产品的差异化与学术价值所在。
   该目的**不是附属功能**，而是一条与主线并行的独立子系统（去 AI 味研究子系统），拥有独立的阶段、数据资产（AI 味素材库）与产出物（规避 skill 库）。

### 1.3 用户与形态
- **用户**：希望借助 AI 创作长篇小说、且在意文本质量的创作者（**面向中文市场**）。
- **形态**：Tauri 2 桌面应用；本地 SQLite 存储；用户自备云端 API Key（应用不代管密钥托管服务）。
- **发布**：GitHub 开源，协议 **MIT**。

### 1.3.1 命名与标识（定稿）
| 用途 | 取值 |
|------|------|
| 应用显示名 | `FateQuill` |
| 中文名 | `命笔` |
| Tauri bundle identifier | `com.fatequill.app` |
| npm 包名 | `fatequill` |
| Cargo crate 名 | `fatequill` |
| GitHub 仓库名 | `FateQuill` |

### 1.4 开发方式（关键约束）
**纯 AICoding**：用户不手写代码，全部由 OpenFeel 流水线完成。
因此本计划的一切任务必须满足：
- **任务明确**：单一交付物、单一职责；
- **验收标准可判定**：能用命令、测试、可见行为或明确清单判定通过与否；
- **避免模糊表述**：不使用「优化体验」「尽量流畅」等不可判定措辞，改为量化指标（如「输入 5000 字章节，编辑区输入延迟 < 16ms」「AI 流式输出期间编辑器组件重渲染次数 = 0」）。

### 1.5 国际化（i18n）需求（定稿，以本节为准）
采用标准 i18n 方案（如 **i18next / react-i18next**），**中英双语可切换**。定位为**界面的双语化，而非内容本地化**：

| 语言 | 范围 |
|------|------|
| **中文版** | 完整功能 + **预置中文创作风格**（用户可自定义/扩展） |
| **英文版** | **仅翻译软件基本信息**（菜单、按钮、设置项等界面文案）；不做任何内容本地化 |

- **创作向能力全部面向中文市场**：创作风格库、设定体系、prompt、审查维度等**不针对英文小说做适配**；英文界面仅在外壳层面呈现中文内容（即英文版 = 英文界面 + 中文创作内容）。
- 英文版不改变任何创作逻辑与数据，仅切换 UI 文案。
- 落点：
  - i18n 基建纳入 **stage-01**（脚手架：i18n 初始化、语言资源目录、切换机制）；
  - 界面文案**双语从 v0.1 起步**（新增 UI 同时提供 zh-CN / en 文案，缺英文项回退中文）；
  - 英文版**基本信息收口**在 **stage-12**（发布阶段完整核对，确保无遗漏的英文界面文案）。

## 2. 技术栈（已定稿，不再讨论替代方案）

| 层 | 选型 | 约束/说明 |
|----|------|-----------|
| 桌面壳 | **Tauri 2**（Rust 后端） | 所有外部 HTTP 请求走 Rust 侧，规避 WebView CORS 限制 |
| 前端 | **React + Vite + TypeScript** | 严格模式；组件与逻辑分离 |
| 样式 | **TailwindCSS + shadcn/ui** | shadcn/ui 为**代码复制型**组件（源码入库、可改），非黑盒依赖 |
| 编辑器 | **Tiptap** | 按**章节分文档**，禁止整本单一巨文档 |
| AI 层 | **Vercel AI SDK** | 多 provider；用户配置云端 API Key |
| 状态管理 | **Zustand** | 轻量；编辑器态与生成态**分离** |
| 国际化 | **i18next + react-i18next** | 中英双语界面；见 §1.5；语言资源按命名空间组织 |
| 本地存储 | **SQLite**（Tauri SQL 插件） | schema 由迁移脚本管理 |
| 密钥存储 | **系统密钥链**（`keyring` / `tauri-plugin-stronghold`） | 不入库、不入 Git（C-05） |
| 测试 | 前端 Vitest + Testing Library；Rust `cargo test`；端到端 WebDriver/Tauri 集成 | 见各阶段验收标准 |

## 3. 整体架构

### 3.1 分层
```
┌─────────────────────────────────────────────────────────┐
│ 表现层  React + Vite + Tailwind + shadcn/ui (Tiptap 编辑) │
│  - 编辑器视图 / 大纲树 / 生成面板 / 设定卡 / 素材库        │
├─────────────────────────────────────────────────────────┤
│ 状态层  Zustand（editorStore / generationStore / uiStore）│  ← 编辑器态与生成态严格隔离
├─────────────────────────────────────────────────────────┤
│ 领域层  novels / chapters / settings / characters / ...    │
│  - 纯 TS 领域模型 + 业务规则（无 UI、无网络）              │
├─────────────────────────────────────────────────────────┤
│ 编排层  Agent Orchestration Engine（可插拔）              │  ← 核心骨架
│  - Agent 角色（推演官/编著官/角色官/审查官/设定官…）       │
│  - Pipeline（阶段可组合）、Model Provider 抽象             │
├─────────────────────────────────────────────────────────┤
│ 桥接层  Tauri IPC（invoke/command）                       │
├─────────────────────────────────────────────────────────┤
│ 后端层  Rust：HTTP 代理(SSE 流式) / SQLite / 文件/密钥存取 │
└─────────────────────────────────────────────────────────┘
```

### 3.2 关键架构原则
1. **可插拔编排引擎**：Agent 角色、Model Provider、Pipeline 阶段均以接口 + 注册表形式组织，新增角色/模型不改动既有代码（面向扩展）；但**不为未确定的未来预留空抽象**，抽象仅在有 ≥2 个真实实现时引入。
2. **状态隔离**：AI 生成过程的流式更新**不触发**编辑器重渲染。生成态独立 store，编辑器仅在收到「提交」动作或显式订阅片段时更新。
3. **章节分治**：一个章节 = 一个 Tiptap 文档实例，避免整本巨文档导致的渲染卡顿与内存膨胀。
4. **Rust 守边界**：网络、密钥、SQLite 等敏感/平台能力集中在 Rust 侧，前端只经 IPC 访问。

### 3.3 核心模块（与阶段对应）
| 模块 | 说明 | 主要阶段 |
|------|------|----------|
| 工程与基础设施 | 脚手架、构建、测试、CI、**i18n 基建** | stage-01 |
| 领域模型与存储 | SQLite schema、迁移、仓储 | stage-02 |
| AI 编排引擎 + 模型配置 | 可插拔引擎骨架、多 provider 配置 | stage-03 |
| 编辑器 | Tiptap 章节文档、卷→章大纲树 | stage-04 |
| 章节生成 | 单 Agent 生成、流式、设定卡 | stage-05 |
| 审查模块 | 剧情/世界观/合规/真人感多维审查 | stage-06 |
| 去 AI 味研究子系统 | 多模型交叉判断、素材库、skill 库 | stage-07 |
| 多温度推演 | 不同温度并行推演 + 克制收敛 | stage-08 |

## 4. 核心里程碑

## 5. 全局约束表

| 编号 | 约束 | 类型 | 判定方式 |
|------|------|------|----------|
| C-01 | 长文渲染：按章节分文档，禁止整本单文档 | 性能（硬） | 单章 5000 字编辑区输入延迟 < 16ms |
| C-02 | 流式渲染：AI 输出增量追加 + 节流重渲染 | 性能（硬） | 流式期间重渲染频率受节流控制（如 ≥ 50ms 合并） |
| C-03 | 状态隔离：生成时编辑器零重渲染 | 性能（硬） | 生成过程中 editorStore 快照不变；可测的重渲染计数为 0 |
| C-04 | 网络走 Rust 侧，前端不经 WebView 直连外网 | 架构（硬） | 代码审查：前端无外部 HTTP 调用 |
| C-05 | 密钥仅存本地，不入库、不入 Git | 安全（硬） | `.gitignore` 覆盖；代码审查 |
| C-06 | 组件优先采用 shadcn/ui 源码入库方式 | 架构 | 审查：无不可改的黑盒 UI 依赖 |
| C-07 | 任务粒度适配 AI 执行，验收标准可判定 | 流程（硬） | 阶段计划任务表逐条具备「验证标准」列 |
| C-08 | 无复用价值的抽象/依赖/扩展点须先确认 | 设计 | 用户/审查确认 |
| C-09 | 每个阶段独立可执行、可审查、可回滚 | 流程 | 阶段 status.md 与 flow.json 一致 |
| C-10 | 「去 AI 味」为独立子系统，不得降级为附属 | 产品（硬） | 阶段计划含独立阶段与数据资产 |
| C-11 | UI 走 i18n，中英双语可切换；创作向能力仅面向中文市场 | 产品（硬） | 新增 UI 均含 zh-CN/en 文案；审查无内容本地化 |
| C-12 | 命名与标识统一为 FateQuill / 命笔 / com.fatequill.app | 架构 | 代码审查：无 NovelCreate 残留 |
